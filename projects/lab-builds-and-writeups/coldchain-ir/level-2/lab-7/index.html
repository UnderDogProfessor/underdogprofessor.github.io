COLD CHAIN Lab 7: spraying one password at a whole company

The second Level 2 lab: spray one password at eight accounts from a Kali VM, then trace it through the file server and the domain controller. My attack tool showed timeouts. The logs showed every guess, and the one that worked.

Level
2, A small company
Time
About 90 minutes
Lab network
Windows Server 2025 domain controller and file server, three Windows 11 PCs, a Kali attacker, in VMware
Evidence
Security logs on the file server and the domain controller, events 4625, 4624 and 4776
Tools
NetExec on Kali, Event Viewer, EvtxECmd and Timeline Explorer

What this is

This is the second lab in Level 2 of COLD CHAIN, a set of hands-on incident response labs I’m building in public around a made-up company, Rimeport Cold Logistics. In Lab 6 I learned what a normal sign-in looks like across Rimeport’s network. In this lab an attacker shows up: a Kali Linux VM at 10.20.99.50, an address nobody at Rimeport owns, on the same private network as everything else. The lab links to Kali’s own pages for getting Kali, and walks through putting it on the lab network and checking it can reach the file server.

The story: late one evening, the file server writes a burst of failed sign-ins, one for almost every person at Rimeport, a few seconds apart. Priya, the IT manager, asks: was someone guessing passwords? Which accounts, from which machine, did any guess work, and why didn’t a single account lock?

What the lab asks

You play the attacker first. On the domain controller, you give Luis Ferreira’s account a “temporary” password a helpdesk might use, Rimeport2026!, and check the lockout policy. From Kali, you then try that one password against eight names with NetExec, including a name that doesn’t exist and a former admin whose account is disabled.

Then you investigate: the file server’s records for each failed and successful sign-in (4625 and 4624), the domain controller’s record of each password check (4776), and the same count again in Eric Zimmerman’s Timeline Explorer.

What I found

  • One guess worked. luis.ferreira signed in at 8:13:40 PM: a 4624 on the file server, Logon Type 3, NTLM, from 10.20.99.50. The domain controller logged the matching password check with no error.
  • The spray took 12 seconds, in 2-second steps. Windows Server 2025 turns on an SMB authentication rate limiter by default, which waits 2 seconds after each failed sign-in. It paused after every failure but not after Luis’s success, so the success stood out by its timing alone.
  • My attack tool and the logs told different stories. NetExec reported every failure as a connection timeout. The file server wrote down each one, with the exact reason it failed.
  • The attacker sent no name. The workstation name was empty on every file server record from the spray, and on the domain controller records I checked. A 4776 has no address field at all, so only the file server’s records pointed at 10.20.99.50.
  • The codes gave away which accounts are real. The made-up name got 0xC0000064, an account that doesn’t exist. Everyone else got 0xC000006A, wrong password, including the disabled former admin. So the log shows that his account exists, but not that it’s switched off.
  • Rimeport’s accounts never lock: the threshold is 0. But Microsoft’s recommended threshold of 10 wouldn’t have stopped this either. One password per account stays far under any sensible limit, which is the whole point of spraying.

What I missed, and what changed because of my run

I pasted one screenshot into my notes but never saved it as a file. I wrote down only three of the eight error codes on the domain controller, and I didn’t record the hashes when I collected the logs. My first answer to “what happened” had the order backwards: I wrote that a compromised account ran the spray, when the spray is what compromised Luis’s account. Event Viewer’s Find also tripped me up, because it only searches down from the record you’ve selected. It’s all in my notes.

The lab changed because of the run. It now quotes NetExec’s real output and explains the timeouts, gives the real timeline with its 2-second steps, says the attacker’s name fields were empty, shows what the disabled account recorded, tells you to start Find from the top, and groups the domain controller’s records by account, workstation and result in Timeline Explorer.

Try it

The setup guide, the lab and my notes are on GitHub, with my screenshots. Kali attacks only the lab’s own machines, on a private network with no way out. Do the lab before reading my notes. Your times will differ.
