COLD CHAIN Lab 1: what normal looks like in the Windows sign-in log

A beginner incident response lab I built and ran on a Windows 11 VM: make a normal morning, then find every step in the Security log. My run found an unlock logged differently from Microsoft's table.

What this is

COLD CHAIN is a set of hands-on incident response labs I’m building in public. Every lab takes place at the same made-up company, Rimeport Cold Logistics, which stores and delivers chilled and frozen food. Level 1 is the basics: one Windows computer, one small thing to find, about an hour each.

Lab 1 asks a simple question: before anything goes wrong, what does a normal morning look like in the log?

What I built

One Windows 11 Enterprise virtual machine in VMware Workstation, named WS-DSP-01: the computer of Dana, a dispatcher at the North Yard warehouse. It has a local account for Dana, the time zone set to Eastern, Windows fully updated, and a clean snapshot to return to before every lab.

What the lab asks

Make a normal morning yourself (sign in, lock the screen, unlock it, restart, sign in again) and write down the time of every step. Then find each one in the Security log as event 4624, a successful sign-in. Your own notes are the answer key.

What I found

  • One sign-in, two records. Dana’s account is an administrator, so each sign-in wrote a linked pair: one with an elevated (admin) token and one without. Each record’s Linked Logon ID points at the other.
  • The unlock logged as Logon Type 2, not 7. Microsoft’s table lists 7 for an unlock. On this build, unlocking looked exactly like signing in, in two separate tests. The only thing that told me it was the unlock was my own written time.
  • Fifty sign-ins in 24 seconds. After the restart, the log recorded 50 successful sign-ins in under half a minute. Four were Dana. The rest was Windows starting itself: SYSTEM, LOCAL SERVICE, NETWORK SERVICE, and the window manager and font driver accounts (DWM-1, UMFD-0, UMFD-1).
  • One open question. Twice, a Dana sign-in appeared right after Windows started and before I typed a password (09:49:26 and 09:58:30). It may be Windows signing her in automatically after a restart and then locking the screen. Microsoft documents a feature that does this, called automatic restart sign-on, and says it’s on by default on computers that aren’t joined to a domain. I haven’t seen the log event that would confirm it, so it stays unconfirmed. I only caught the first one when I read my full log later.

What changed because of my run

Running the lab myself changed it. The first draft said the window manager and font driver accounts appear at every sign-in; my logs showed them only at startup, so the lab now says that, with an explainer on what they are. The unlock answer now tells learners to check their own result instead of trusting the table. Setup now finishes Windows updates before the snapshot, and the lab says to restart Part 1 if you miss a timestamp. I forgot the timestamps on my first attempt.

Try it

Everything is on GitHub: the setup guide, the lab, and my notes, including the exported .evtx files so you can open my logs yourself. Do the lab before reading my notes. Your times will differ, and that’s the point.
