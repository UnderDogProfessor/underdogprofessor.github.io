COLD CHAIN Lab 4: finding a task that runs at every sign-in

A beginner lab where you set a task to run at every sign-in, then trace it through Task Scheduler and the Windows Security log. In my run, the record of its deletion kept the name and nothing else.

Level
1, Basics
Time
About 45 minutes

Windows 11 Enterprise Evaluation, build 26100, in VMware Workstation
Evidence
Security log, events 4698, 4699 and 4624, and schtasks

What this is

This is the fourth lab in COLD CHAIN, a set of hands-on incident response labs I’m building in public around a made-up company, Rimeport Cold Logistics. It uses the same Windows 11 virtual machine as Lab 3.

The story: Dana says her computer “does something” every time she signs in, and nobody in IT installed anything new. Is something set up to run at every sign-in? If so, what is it, who set it up, and when?

What the lab asks

You play the intruder. First you check that Windows records scheduled tasks at all, because that audit setting is a separate one. Then you create a task with a name that looks like IT made it, PrintDriverUpdate, set to run at every sign-in with the highest rights the account has. You restart, prove the task ran, and trace it three ways: in Task Scheduler, in the Security log as event 4698 (a scheduled task was created), and with schtasks /query. Finally you delete it and see what event 4699 (a scheduled task was deleted) keeps.

What I found

  • Windows wasn’t recording it until I turned it on. The setting that records scheduled tasks said No Auditing on my VM.
  • Created at 11:20:40 AM by Dana’s admin session. The task’s full contents are inside the 4698: who made it, that it runs at sign-in, that it runs with the highest rights, and the exact command. Its Logon ID matched the Elevated Token Yes half of Dana’s sign-in, the match I couldn’t make in Lab 3 because I had cleared the log.
  • It ran 3 seconds after I signed in. I signed in at 11:22:14 after the restart, and Windows says the task last ran at 11:22:17. The proof file it writes was stamped 11:22 with one line in it, so two separate sources agree.
  • I wasn’t the only one making tasks. Two minutes before mine, OneDrive deleted and re-created its own task, and the log names Dana as the account that did it. Windows updated its own tasks 36 times in about ten minutes. Edge and OneDrive tasks also share the top folder with mine. A new task isn’t suspicious by itself. What it runs is.
  • The deletion record kept the name and nothing else. Microsoft’s page for 4699, written for Windows 10, says it holds the full deleted task. On my Windows 11 VM its contents were empty, so the creation record was the only full copy.

What I missed, and what changed because of my run

I didn’t write times as I went, so every time in my notes comes from the log or a screenshot clock. I typed /get instead of /set the first time I changed the audit setting, and my first screenshot of the 4698 was OneDrive’s task, not mine. The window the lab’s story promised at sign-in was too quick for me to notice, because the task only writes one line. It’s all in my notes.

The lab changed because of the run. It now warns that filtering for 4698 shows tasks Windows and apps make themselves, says the top folder is a reason to look rather than proof, asks which sign-in created the task, and says the 4699 may not keep the task’s contents, so you export the creation record before you delete anything.

Try it

The lab is on GitHub, and so are my notes, my screenshots and my exported .evtx logs, so you can open the real records in Event Viewer. Do the lab before reading my notes. Your times will differ.
