An old SID still opens doors

SID history lets a migrated account carry its previous identifier, so access written against a retired domain keeps working years afterwards.

Every account has a security identifier, a SID, and permissions are written against SIDs rather than names. Rename an account and its access follows, because the name was never the thing holding the permission.

Migrate an account to a different domain and it gets a new SID. Every permission in the old domain still names the old one. Rather than rewrite every access control list in the estate, migration tools copy the old SID into an attribute called SID history, and the domain controller puts it in the ticket alongside the new one.

So the account authenticates as its new self and is authorized as both.

That is a sensible design for a migration lasting a few months. The problem is that it is almost never cleaned up afterwards. Years later, accounts are still carrying identifiers from domains that were decommissioned, and nobody can read what access that grants, because the resources those SIDs named may be gone or may have been rebuilt since.

It is also a writable attribute. An account that can set SID history on another account can hand it privileged access without touching a single group, and without showing up anywhere in a membership report.

Query your directory for accounts where sIDHistory is populated. Anything pointing at a domain you no longer run is a leftover rather than a control.

CHECK YOURSELF

An account was migrated from a retired domain three years ago. Its group memberships are all unprivileged, yet it has administrative access to a file server. What is the likeliest reason?

SHOW THE ANSWER

Permissions on the server still name the old identifier, which the account carries in SID history

Why. Permissions are written against security identifiers rather than names, so a list built before the migration still names the old one. The account presents both identifiers, the server matches the old entry, and the access is granted. Nothing has failed and nothing is stale in the way the first two options suggest. A surviving trust is a reasonable guess, but SID history exists precisely so that access survives without one, which is why the retired domain can be gone entirely and this still works.
