MFA is checked at the door

Multi-factor authentication runs when a session is issued. A stolen session never meets it, which is why token theft became worth the effort.

Multi-factor authentication runs once, at sign-in. After that the user holds a session, and the session is what gets presented.

So an attacker who obtains that session skips the factor entirely. No prompt arrives on anybody’s phone, because nothing is authenticating. Something is being presented that was already authenticated.

This is why stealing tokens became worth doing. Phishing a password used to be enough, MFA made the password insufficient, and the target moved from the credential to the thing the credential produces. A relay page that forwards a real login to the real site in real time collects the session, and the session is the part that works.

Two consequences follow for defenders. MFA coverage figures describe your sign-in surface and say nothing about session theft. And a policy evaluated at sign-in is evaluated once, so a session issued from a compliant device stays valid after the device stops being compliant, unless something re-evaluates it.

The counter is to reduce what a stolen session is worth. Bind tokens to a device where the platform supports it, keep lifetimes short enough that theft has a deadline, and turn on continuous evaluation if your provider offers it.

Take one conditional access policy you rely on. Find out whether anything re-evaluates it after the session has been issued.

CHECK YOURSELF

Your tenant enforces MFA on every sign-in. An attacker phishes a user through a relay page and reaches the mailbox, and no MFA prompt ever reaches the user. How?

SHOW THE ANSWER

The relay captured the issued session, which is presented instead of authenticating again

Why. A relay page sits between the user and the real service, so the user completes the genuine MFA challenge and the attacker takes what it produces. Nothing authenticates afterwards, so nothing prompts. The other three are all real MFA bypasses and each leaves different evidence: a legacy protocol appears as a different authentication type in the logs, an approved prompt means the user did see something, and an exclusion would be visible in the policy itself. The scenario says no prompt reached the user at all, which points at the session rather than the policy.
