A password reset does not end a session

Resetting a compromised account's password feels like containment. Every session issued before the reset usually keeps working.

An account is compromised. You reset the password. The attacker keeps working.

This surprises people every time, and it should not, because it follows from how sessions work. Authentication happens once. What the user carries afterwards is a session: a cookie, a token, a ticket, depending on the system. That artefact is what proves them on every subsequent request, and it was issued before you changed anything.

The password is an input to the issuing step. It is not consulted again until the session expires and something has to issue a new one.

So a password reset closes the door for the next person who tries to walk through it. It does nothing about anyone already inside, and an attacker who has been there long enough to be noticed is holding a session.

Revoking sessions is a separate action with a different name in every product: sign out everywhere, revoke refresh tokens, reset sign-in sessions, invalidate tickets. Find yours before you need it, because the middle of an incident is a poor time to go reading an admin console.

There is a second order to this. Some sessions renew themselves, so one can stay alive indefinitely without the password ever being presented again.

Take one account in your identity provider. Reset its password, then check whether its existing sessions still work.

CHECK YOURSELF

An attacker is active in a cloud mailbox. You reset the account password and confirm the new one works. What should you expect?

SHOW THE ANSWER

The attacker keeps access until their session is explicitly revoked or expires

Why. A session is issued at authentication and presented on every later request in place of the password, so changing the password does not invalidate it. Revocation is a separate action, and in most products it has its own name and its own button. The first option describes how people imagine it works rather than how any mainstream system behaves. Reconnection does not help either, because the client presents the session it already holds. The last option is the tempting one and describes a different attack: capturing the new password would give fresh access, and the attacker does not need it while the old session still answers.
