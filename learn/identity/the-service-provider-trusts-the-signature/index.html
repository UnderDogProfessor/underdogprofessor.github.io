A SAML application trusts the signature, not the user

A service provider never sees the password. It checks a signature against a certificate somebody configured, which makes the signing key a root of trust.

In SAML, the application you are logging into never sees your password. It sees an assertion: a signed XML document saying that an identity provider vouches for this person.

The application checks that signature against a certificate it was configured with in advance, by somebody doing an integration, probably through a web form. If the signature holds, the user is in.

Read that again, because the trust sits somewhere people do not expect. The service provider does not trust the user. It trusts whoever holds the key that signs assertions.

Several things follow at once. It is why a SAML integration breaks every time a signing certificate rotates and nobody told the other side. It is why the configuration screen asks you for a certificate rather than a credential. And it is why an attacker able to sign assertions needs nobody’s password: they can mint a user, including one whose assertion claims that MFA was satisfied, which the application has no way to verify independently.

That last point is the reason a signing key belongs in the same mental category as a domain controller. Not a configuration item. A root of trust.

Go and find out where your identity provider’s SAML signing key lives, who can export it, and when it last rotated. If the list of people who can export it takes a while to write down, that is your finding.

CHECK YOURSELF

An attacker obtains the private key your identity provider uses to sign SAML assertions. Which statement best describes what that gives them?

SHOW THE ANSWER

They can produce valid assertions for any user in any federated application, with no need for those users' credentials or MFA

Why. A service provider's whole check is whether the assertion carries a valid signature from the certificate it was configured to trust. It has no view of how the user authenticated, so an assertion that claims MFA was satisfied is accepted on the strength of the signature alone. Assertions are not bound to an existing session, signing needs only the identity provider's private key, and the service provider has no copy of the user database to check anything against. That is the whole reason the signing key sits in the same risk category as a domain controller.
