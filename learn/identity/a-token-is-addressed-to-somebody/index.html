A token is addressed to somebody

The audience claim names which service a token was minted for, and a service that does not check it will happily accept one issued for somewhere else.

Every token carries a claim saying who it is for. In a JWT it is aud, the audience, and it names the service the token was minted to be presented to.

Validation is where this goes wrong. Checking a token usually means three things: the signature is good, it has not expired, and the issuer is one you trust. Those are the checks people remember. The fourth, that the audience is you, is the one that gets skipped, because the token works without it.

Skipping it has a specific consequence. If two services trust the same identity provider, and neither checks audience, a token for one is a token for the other. An attacker who can obtain a token for the least important service in your estate now holds one the most important service will accept.

Nothing about that is an attack on the identity provider. It issued a perfectly correct token for the thing it was asked about. The receiving service chose not to read the address on the envelope.

This is also why a single shared audience value across many services, a pattern that shows up when somebody wanted to stop fighting configuration, quietly undoes the separation you thought you had.

Pick one internal API and read its token validation. Count how many of the four checks it performs. The audience one is where the money is.

CHECK YOURSELF

Two internal services, a reporting tool and a payments API, both trust tokens from the same identity provider. The payments API validates the signature and the expiry but not the audience. What follows?

SHOW THE ANSWER

A valid token minted for the reporting tool can be replayed against the payments API

Why. The signature only proves the issuer minted the token and nobody altered it. It says nothing about intended recipient, and in this setup both services trust the same issuer and therefore the same key. The audience claim is the part that carries the destination, so skipping it collapses two trust boundaries into one. Whoever can get a token for the low-value service now has one the high-value service accepts, which is a privilege escalation that never touches the identity provider.
