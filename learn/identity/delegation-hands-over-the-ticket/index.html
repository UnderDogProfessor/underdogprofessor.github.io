Delegation hands over the ticket, not the task

Unconstrained delegation stores a copy of the user's ticket-granting ticket on the service, so compromising that service inherits every user who visited it.

A service that needs to reach a database on your behalf has a problem. It has your ticket for itself, and that ticket is no good anywhere else.

Delegation is the answer Kerberos gives. The unconstrained version solves it bluntly: the client forwards its ticket-granting ticket, and the service keeps a copy in memory so it can request tickets as you, to anything.

Read that again with an attacker in mind. Every user who authenticates to a server trusted for unconstrained delegation leaves a reusable copy of their identity on it. Not a hash to crack. Not a logon record. A working ticket.

So the value of that server is not its data. It is whoever has visited it. One domain administrator browsing to a print server once is enough, and nothing in the authentication logs looks unusual, because nothing unusual happened.

Constrained delegation exists to narrow this: the service may impersonate you, but only to a named list of services. Resource-based constrained delegation inverts the trust so the target service decides who may impersonate users to it, which is the version you want.

Go and list which computers and accounts in your domain hold unconstrained delegation. On most estates the list is short, old, and nobody remembers approving it.

CHECK YOURSELF

A web server is configured for unconstrained delegation. A domain administrator browses to it once. What has the server now got?

SHOW THE ANSWER

A copy of the administrator's ticket-granting ticket, usable to act as them until it expires

Why. Unconstrained delegation works by having the client forward its TGT, which the service caches in memory so it can impersonate that user to anything. The caching happens on authentication, not when the service actually calls onward, so a single visit is enough. No password or hash is involved, which is why this leaves no failed-logon trail and why ticket lifetime, not a password reset, decides how long it is useful.
