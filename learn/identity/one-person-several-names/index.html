One person, several names

A single account carries several names at once and different systems log different ones, so matching two records by name is a guess rather than a join.

One account carries more names than people expect. A down-level name for older protocols. A user principal name that looks like an email address and often is not one. A display name. A mail attribute. A security identifier that never changes. In a cloud directory, an object ID as well.

Systems log whichever one they happen to hold. A Windows event records the down-level form. A web application records the principal name. A SaaS audit trail records the address the account was invited with, which might be an alias from two jobs ago.

Now two alerts land, and somebody has to decide whether that is one person or two before the timeline means anything.

Matching on names gets this right most of the time, which is the problem. It fails on the cases that matter: the contractor with two accounts, the person whose surname changed last spring, the shared mailbox, the two people who genuinely hold the same short name in different domains.

The join that holds is the identifier nobody can edit. The security identifier, or the directory object ID. Everything else is a label that somebody in HR can change on a Tuesday afternoon without telling you.

Go and pick one user, write down every name they currently carry, then check which of those your SIEM actually stores.

CHECK YOURSELF

Two alerts arrive. A Windows event names an account in its down-level form, and a SaaS audit log names john.smith@corp.example. What settles whether these are the same person?

SHOW THE ANSWER

The immutable identifier behind each one, such as the security identifier or the directory object ID

Why. Every name on an account is a label somebody can edit, and several of them are routinely edited: surnames change, mail attributes get aliases, principal names get rewritten during a migration. The identifier that survives all of that is the one to join on. Display names are not unique and never were. Device correlation is useful supporting evidence but fails for anyone who uses two machines. The principal name prefix frequently matches the down-level name, which is precisely what makes it dangerous to rely on: it is right often enough to be trusted and wrong exactly where it matters.
