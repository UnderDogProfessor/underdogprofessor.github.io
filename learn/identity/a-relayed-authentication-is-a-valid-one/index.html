A relayed authentication is a valid one

In a relay the attacker never learns the password or the hash. They forward your proof to a different service, which accepts it as genuine, because it is.

NTLM proves you know a secret without sending it. The server issues a challenge, you return a response computed from your password hash, and the server checks the arithmetic.

Notice what is missing. Nothing in that exchange says which server the challenge came from.

So an attacker who can get a machine to authenticate to them has no need to crack anything. They take a challenge from a second server, pass it along as their own, take the response, and hand it onward. The second server sees a correct answer to the challenge it issued, and does what correct answers earn.

The account is yours. The privileges are yours. The record on the receiving end is a successful logon by an account that is supposed to log on, which is why this is hard to find afterward and easy to miss while it happens.

The defense is to bind the authentication to something that cannot be carried elsewhere. SMB signing and LDAP signing tie the session to the exchange that established it. Channel binding ties it to the TLS channel underneath. Where those are enforced, a forwarded response does not fit the session it arrives in.

Go and check whether SMB signing is required on your file servers and domain controllers, rather than merely enabled.

CHECK YOURSELF

An attacker gets a server to authenticate to a host they control, and forwards that authentication to a file server. What does the file server record?

SHOW THE ANSWER

A successful authentication by the coerced account, indistinguishable from a legitimate one

Why. The response the file server checks is a correct answer to the challenge the file server issued, computed by the real account. Nothing in the exchange identifies which host originally asked, so the record is a genuine logon by a legitimate account, which is exactly why relay survives log review. The attacker's own identity never appears, no failure is produced, and no delegation flag is set, because no delegation took place. Signing and channel binding are the controls that help, since they tie the authentication to a session the attacker cannot forward it into.
