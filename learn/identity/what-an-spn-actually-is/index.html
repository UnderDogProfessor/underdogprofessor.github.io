What an SPN actually is

A Service Principal Name maps a service to the account that runs it, and Kerberos refuses to guess when that mapping is wrong.

A Service Principal Name answers one question: which account runs this service?

When you connect to a file server, your machine does not ask for a ticket to “that box over there”. It asks for a ticket to a name, something like cifs/fs01.corp.example. The domain controller looks that name up, finds the account it is registered to, and issues a ticket encrypted for that account.

So an SPN is a mapping. Service name to account. Nothing more than that.

Two consequences fall straight out of it.

Register the SPN to the wrong account and authentication fails in a way that looks like a network problem. The client receives a ticket built for an account that is not the one listening, the service cannot decrypt it, and somebody spends an afternoon reading firewall rules.

Register the same SPN twice and Kerberos refuses to guess. Duplicate SPNs are a classic cause of intermittent failures that hit some users and not others, because the client quietly falls back to NTLM when the Kerberos exchange does not work.

That second one earns its place in a defender’s head. A sudden rise in NTLM authentication to a service that normally uses Kerberos is often somebody having changed an SPN, and occasionally it is not.

Go and list which accounts in your domain hold SPNs. The list is usually shorter than people expect, and every entry on it is a service account worth knowing by name.

CHECK YOURSELF

A web application that has always authenticated users over Kerberos starts showing a sharp rise in NTLM authentication. The clients did not change. What is the most likely cause to check first?

SHOW THE ANSWER

The service's SPN was changed, removed or duplicated, so the Kerberos exchange fails and clients fall back

Why. Kerberos has to resolve a service to exactly one account before it can issue a ticket. A missing, wrong or duplicated SPN breaks that lookup, and Windows clients fall back to NTLM quietly rather than raising an error, which is why the symptom shows up as a protocol shift rather than a failure. Ticket capacity is not a resource that runs out this way. Password expiry produces authentication failures, not a change of protocol. And Kerberos is preferred wherever it works, regardless of whether NTLM is also enabled.
