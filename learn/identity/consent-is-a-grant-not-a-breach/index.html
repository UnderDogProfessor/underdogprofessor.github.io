A consent screen is an authorisation decision

When a user approves an application's access request nothing is broken into. The access is granted, recorded, and survives a password change.

An application asks for access to a user’s mail. The user clicks accept. The application reads their mail.

Nothing failed. No control was bypassed, no credential was stolen, and the audit trail shows a legitimate grant made by a legitimate user who was legitimately authenticated, quite possibly with MFA.

That is what makes consent attacks awkward. The usual containment reflexes do not apply. Resetting the password changes nothing, because the application never held the password. It holds a grant, usually with a refresh token behind it, and grants outlive password changes by design.

The grant is also scoped, and the scope is where the surprise lives. A user approving access to their own mail may be approving rather more than they pictured, depending on what the application asked for and on whether an administrator can consent for everybody at once.

So two controls are worth knowing you have. Restricting who may consent, so ordinary users cannot hand arbitrary third parties access to their data. And reviewing what is already granted, which in most organisations has never been looked at.

Containment here means revoking the grant, not resetting the account.

Open the enterprise applications list in your identity provider. Count how many can read mail or files, and find out who approved each one.

CHECK YOURSELF

A user approves a third-party application that then reads their mailbox. You reset the user's password and enable MFA. What have you achieved?

SHOW THE ANSWER

Nothing against this access, because the application holds a grant rather than the password

Why. An authorisation grant is independent of the password. The application was issued its own tokens and presents those, so it never re-authenticates as the user and never encounters the new password or the new MFA requirement. The third option is the closest to correct and still wrong, because a refresh token renews access without any user involvement, so expiry is not a containment mechanism. Who approved the application changes the blast radius rather than whether revocation is needed. The action that contains this is revoking the grant.
