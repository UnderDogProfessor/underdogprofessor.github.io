Tokens in a URL end up in logs

The implicit flow returned access tokens in the browser address bar, which put credentials into history, referrer headers and proxy logs, and is why it was deprecated.

The implicit flow handed an access token straight back in the redirect, sitting in the browser’s address bar. It existed for a good reason: browser apps had no safe place to keep a client secret, so skipping the token exchange looked like the pragmatic answer.

Then people noticed where URLs go.

They go into browser history. They go into referrer headers when the page links onward. They go into proxy logs, load balancer logs and web server access logs, written whole, because logging the full request line is the default everywhere. They go into the message somebody sends when they copy the address bar to share a page.

A bearer token in any of those is a working credential, and the people with access to a log archive are not the people the token was issued to.

The replacement is the authorization code flow with PKCE. What comes back in the URL is a short-lived single-use code, worthless without a verifier the client holds and never transmits in the first leg. The code can leak into every log in the chain and still be useless.

The general lesson outlives OAuth. Anything in a query string or fragment is written down somewhere you do not control. Go and check whether any of your applications still put credentials, tokens or reset keys in a URL.

CHECK YOURSELF

A team proposes returning an access token in a redirect URL fragment to avoid adding a backend. Beyond the spec advising against it, what is the concrete problem?

SHOW THE ANSWER

The token lands in browser history, referrer headers and anything that logs full URLs

Why. A URL is treated as metadata by everything it passes: saved in history, handed onward in referrer headers, written whole into proxy and server logs, and shared when somebody copies the address bar. A bearer token in that position is a working credential in every one of those places. Fragments do travel inside TLS and tokens remain signed regardless of transport, so those two answers describe problems that do not exist. The authorization code flow with PKCE exists so the thing in the URL is a single-use code instead.
