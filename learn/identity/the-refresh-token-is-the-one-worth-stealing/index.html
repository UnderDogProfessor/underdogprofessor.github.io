The refresh token is the one worth stealing

OAuth issues a short-lived access token and a long-lived refresh token, and most containment steps only deal with the first one.

OAuth hands out two tokens, and people guard the wrong one.

The access token is short-lived. Fifteen minutes, an hour, somewhere in that range. It travels with every API call, so it turns up in proxy logs, in error reports, in traces. It also stops working almost immediately.

The refresh token is the other one. Its entire job is to obtain new access tokens without making the user log in again, so it has to last. Days, often weeks, in some products until something explicitly revokes it.

Take an access token and you have a short window. Take a refresh token and you have an authentication method.

That asymmetry changes what containment means. Forcing a password reset does nothing to a refresh token. Clearing sessions usually does not either, because the token is held at the authorization server rather than by the application the user was in. It has to be revoked where it was issued, deliberately, and in plenty of products that lives on a different screen from the one a responder reaches for first.

So find out now, while nothing is on fire, where refresh tokens are revoked in your stack. Write the path down and put it in the runbook. Discovering that it is three menus deep is a bad thing to do at two in the morning.

CHECK YOURSELF

An attacker took both an access token and a refresh token from a user's workstation. You reset the password and revoked active sessions. What is the most likely remaining path back in?

SHOW THE ANSWER

The refresh token, which commonly survives both a password reset and a session revocation until it is revoked at the authorization server

Why. A refresh token exists so that a user does not have to log in again, which means it is designed to outlive the events that end a login. In many implementations a password reset does not touch it and neither does clearing sessions, because it is held and honored by the authorization server rather than by the application. The access token is the lower-value half: it expires on its own, usually within the hour. And the password is the one thing the reset did deal with.
