COLD CHAIN Lab 8: following one stolen account across a network

The third Level 2 lab: use the password Lab 7's spray found to look around Rimeport from Kali, then follow that one account across the servers. Six sign-ins, six password checks, and nothing on the staff PCs.

November 25, 2026

  • Level2, A small company
  • TimeAbout 90 minutes
  • Lab networkWindows Server 2025 domain controller and file server, three Windows 11 PCs, a Kali attacker, in VMware
  • EvidenceSecurity logs on the file server, the domain controller and a staff PC, events 4624 and 4776
  • ToolsNetExec on Kali, Event Viewer, EvtxECmd and Timeline Explorer

What this is

This is the third lab in Level 2 of COLD CHAIN, a set of hands-on incident response labs I’m building in public around a made-up company, Rimeport Cold Logistics. In Lab 7 an attacker on a Kali Linux VM at 10.20.99.50 sprayed one password at the whole company and got into Luis Ferreira’s account.

This lab picks up from there. Nobody has reset anything yet, and Priya, the IT manager, asks: they had Luis’s password, so where did they go with it, and what could they see?

What the lab asks

You play the attacker again, this time as Luis. From Kali, with NetExec, you try his password on all five Windows machines at once, list the shared folders on the two servers, and ask the domain controller for every account in the domain.

Then you follow that one account: its sign-ins on the file server (4624), its sign-ins and password checks on the domain controller (4624 and 4776), a staff PC’s log, and the whole evening again in Eric Zimmerman’s Timeline Explorer, grouped by computer.

What I found

  • Two machines let the account in. The domain controller and the file server both accepted Luis’s password, and neither said Pwn3d!, so his account isn’t an administrator there. NetExec printed nothing at all for the three staff PCs, and their logs had nothing from 10.20.99.50.
  • An ordinary account sees a lot. Luis could read and change the Dispatch folder, read NETLOGON and SYSVOL on the domain controller, and pull the names of all 11 accounts in the domain. NetExec also showed every share’s description, even for the ones he couldn’t open, so the attacker now knows what Finance and Evidence hold.
  • Six sign-ins, six password checks. Kali signed in to the domain controller four times and the file server twice. The domain controller logged a 4776 for each one, the file server’s included. The 4776s carry no address, so it’s the 4624s that tie the account to 10.20.99.50. One command, the user list, signed in twice in the same second.
  • It didn’t look like a Rimeport PC. Every sign-in was NTLM from 10.20.99.50. Dana’s real sign-in to the file server in Lab 6 was Kerberos from 10.20.20.11. The empty workstation name didn’t help: Dana’s was empty too.
  • Nobody stayed signed in. Timeline Explorer showed a logoff in the same second as every sign-in. NetExec signed in, did its job and left.
  • What the logs can’t say: whether anything in Dispatch was opened or changed. That needs file share auditing, which Rimeport doesn’t have turned on yet.

What I’d tell Priya

Between 7:09 and 7:15 PM, a computer that isn’t ours (10.20.99.50) used Luis’s password to sign in to the file server and the domain controller, found it could read and change the Dispatch folder, and got a list of every Rimeport account, but it couldn’t open Finance or Evidence and never reached a staff PC. First, reset Luis’s password so it stops working for them, then turn on file share auditing so we can find out whether anything in Dispatch was opened or changed.

What I missed, and what changed because of my run

My notes put one Kali command at the wrong time. My first answer to “how could you tell” leaned on the empty workstation name, which proves nothing here. My first answer for Priya said to end Luis’s active sessions, and the logs show there weren’t any. I also ran the timeline commands on the domain controller instead of my investigation PC, where the tools are.

The domain controller refused to save its log export into C:\Evidence, even though I was a domain admin in an elevated window and the file server took the same command. Saving into my Documents folder worked. I still don’t know why, so every Level 2 lab now saves there.

One thing I can’t explain yet: the domain controller’s record of Luis’s sign-in says Elevated Token: Yes, and the file server’s says No. Luis isn’t an administrator anywhere. It’s written down as an open question in my notes and in the lab.

The lab changed because of the run. It now gives the real counts and the real share list, warns about NetExec’s setup lines on its first run, tells you to read the account and address before counting a record (the staff PC’s records at 7:09 PM were its own services, not Kali), and points out the logoffs and older records in Timeline Explorer.

Try it

The setup guide, the lab and my notes are on GitHub, with my screenshots. Kali attacks only the lab’s own machines, on a private network with no way out. Do the lab before reading my notes. Your times will differ.
