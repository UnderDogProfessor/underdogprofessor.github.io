The integrity checker said it was clean

Volexity found UTA0576 chaining three Ivanti zero-days on a fully patched device. No malware, and the Integrity Checker reported clean.

SHREYAS LIPARE · GCIH · CEH MASTER

Anyone running an internet-facing VPN appliance, and anyone whose compromise assessment for one begins and ends with the vendor's integrity checker.

Researched and drafted with AI assistance, then reviewed and edited by Shreyas Lipare before publication. Every source below was checked against the original.

The appliance was fully patched. Volexity names the build: 22.8R2.4, Build 19097 [1].

The Integrity Checker Tool, which is the thing Ivanti tells you to run to find out whether one of these devices has been tampered with, reported nothing. No malware was written to disk. No web shell was dropped.

And an actor Volexity tracks as UTA0576 was reading the organization’s LAPS local administrator passwords and BitLocker recovery information out of Active Directory [1].

What happened

On October 5, 2026, Volexity began investigating suspicious activity on an Ivanti Connect Secure device belonging to a network security monitoring customer. It found exploitation running since at least October 3 [1].

The route in was three vulnerabilities used together. An authentication bypass in the welcome.cgi component let unauthenticated requests reach CGI endpoints that are supposed to be protected. A file write flaw in the wu.cgi upload handler, which writes an uploaded file to disk before it checks whether the file is a valid archive, created a window to execute it. That gave code execution as the cgi-server user. A third flaw, in how the dsinvoked broker trusts DSCache configuration data, took that to root [1].

Ivanti published an advisory on October 13 covering the first two as a single issue, CVE-2026-104935, an authentication bypass by spoofing, CWE-290, scored 8.6 high [2]. NVD carries the same score [3]. CISA added it to the Known Exploited Vulnerabilities catalog the same day with a remediation date of October 16, 2026 [4].

The third flaw, the privilege escalation, has no CVE identifier and no patch. Ivanti says it is developing additional updates to address it [5].

Fixed versions are 25.1.1.2, 25.1.3.0, 25.1.3.1 and 22.8R2.5. Versions 22.7R2.14 and earlier are not affected [2].

Why this matters

Appliance compromises are routine now and most of them produce a familiar cleanup: find the web shell, pull the sample, hunt the hash estate-wide. This one offers none of that, and the absence is deliberate.

Volexity states plainly that it “did not identify first-stage malware or web shells” [1]. Instead of installing anything, UTA0576 re-exploited the device for each command and passed results back over the same HTTPS channel the exploit used. There is no implant because there did not need to be one.

That removes the artifact most detection programs are built around. Your EDR has nothing to quarantine. Your threat intel feed has no hash to match. The IOC section of the report is short because there is very little that persists.

The second thing worth your attention is a sentence in Ivanti’s own advisory that I have not seen quoted anywhere. Ivanti says it found part of this vulnerability itself, through its product security program, and fixed it in the July release 25.1.3.0, then worked on backporting the fix to the remaining supported versions when exploitation began [2].

So a fix existed in July. Three months before anybody was attacked.

Read a few paragraphs further in the same advisory and you find why that did not help most customers. Moving to 25.1.3.0 requires new hardware: the ISA4500, ISA6500 or ISA8500, with virtual deployments needing to be rebuilt from a new template [2]. The branch carrying the fix was not somewhere an existing customer could simply go. The ones who could take a fix inside a maintenance window were waiting on the backport, and the backport was still in flight.

Ivanti told CyberScoop the original issue “did not meet the threshold for an out-of-band release” [5]. I think that judgement is defensible on the information available in June and still worth examining, which is a different claim from saying somebody was negligent.

Technical breakdown

The chain and the controls that sever it:

Four of the seven steps have a control that breaks them. The three that do not are the ones the defender cannot reach: the unpatched escalation, the in-memory evasion that makes the vendor’s own verification tool return a false negative, and an exfiltration path that is the same HTTPS session the exploit already owns.

That evasion deserves a sentence of its own, because it is the part that will mislead people this week. The chain patches libdsplibs.so in memory and restores the DSCache data it alters afterwards. The Integrity Checker Tool compares what is on disk. Nothing on disk changed, so the tool reports clean, and it is not malfunctioning when it does. It is answering the question it was built to answer. The question a responder needs answered is a different one.

Volexity also records that the actor tampered with debuglog and audit.log, deleted its own scripts, restored the patched memory and suppressed command output, while noting that how completely those steps succeeded “has not been fully established” [1].

On attribution, Volexity assesses with low confidence that UTA0576 has criminal rather than espionage motivations, and with high confidence that the activity was preparation for lateral movement [1]. It also assesses with medium confidence that the actor used large language models in exploit development and post-exploitation work [1]. UTA0576 is a Volexity activity cluster designation, not a named group with public attribution, and it should be written up that way internally.

What defenders should do next

Immediate, today. Patch. CVE-2026-104935 is in KEV with a remediation date of October 16, 2026, carries an EPSS probability in the 98th percentile, and high-quality public exploit code exists [3][4]. If you run 22.8R2.4 or earlier, 25.1.2.2 or earlier, or 25.1.1.1 or earlier, you are in scope [2]. Shadowserver counts more than 5,500 of these appliances exposed to the internet [6].

Near term, this week. Treat a clean Integrity Checker result as non-evidence. If the device was reachable and unpatched at any point since late September, your compromise assessment needs network and memory forensics, not a tool run. Then rotate credentials on the appliance, and specifically rotate the Active Directory service account it uses, which is the account that did the directory searching in this intrusion and is the one most likely to be left alone during a rebuild.

Search your directory logs for reads of the LAPS and BitLocker attributes above. Do this whether or not you run Ivanti, because the technique is not appliance-specific and the detection is cheap.

Structural, this quarter. Two questions for your architecture, both of which this incident answers badly. What can the VPN appliance’s service account read in Active Directory, and why does it need to? And if your vendor shipped a fix that required new hardware, what is your plan for the branch you are actually on? That second one is a procurement question wearing a security costume, and it will decide how long you sit on a known-vulnerable build the next time.

Checklist

  • Are we on 25.1.1.2, 25.1.3.0, 25.1.3.1 or 22.8R2.5, or still on an affected build?
  • Was the appliance internet-reachable and unpatched at any point since September 30?
  • Does our compromise assessment rest on the Integrity Checker Tool alone?
  • What Active Directory rights does the appliance’s service account hold?
  • Have we rotated that service account, not just the admin credentials?
  • Do we log and alert on reads of LAPS and BitLocker recovery attributes?
  • Do we have network capture or memory from the device, or only its own logs?

A clean result is not a negative result

The failure worth naming here is not Ivanti’s backport schedule, though that will get the attention. It is that an entire industry has agreed to accept vendor-supplied integrity tools as compromise assessment for appliances we are not permitted to inspect ourselves.

These devices ship as sealed boxes. You cannot install an agent, you often cannot get a shell, and the vendor hands you a checker and a recovery procedure. That arrangement works precisely until somebody builds a chain that operates in memory and restores what it touched, at which point the checker returns clean and the organization has no independent way to disagree with it.

UTA0576 did not defeat a control that failed. It defeated a control working as designed, by operating outside the scope that control was ever built to cover. If your assessment of an internet-facing appliance cannot survive the vendor’s tool returning a false negative, then you do not have an assessment. You have a vendor’s opinion, and this week it was wrong.

FREQUENTLY ASKED

We patched and the Integrity Checker Tool came back clean. Are we fine?
Those two results together are exactly what the victim in Volexity's report had. The chain modifies library code in memory only and restores the configuration data it alters, so the tool finds nothing to report, and the actor deployed no malware or web shell for anything to find on disk. A clean checker result means the checker found no persistent modification, which is a narrower statement than it sounds. Confirming or excluding compromise here takes network and memory forensics.
What exactly was the attacker after?
The credentials that protect your other credentials. A custom LDAP tool authenticated to a domain controller using the appliance's own Active Directory service account, then searched for LAPS local administrator passwords, BitLocker recovery information, and attributes holding passwords in plaintext. LAPS exists to stop local administrator reuse across machines and BitLocker recovery keys exist so you can get data back. An actor holding both has your lateral movement control and your recovery path.
Is the whole chain patched now?
No. Ivanti patched the authentication bypass and the remote code execution together as CVE-2026-104935 on October 13, 2026. The third component, a privilege escalation to root, had no fix and no CVE identifier when I checked on October 15, and Ivanti has said a fix is coming in a future release. That matters less than it sounds for most defenders, because the escalation is only reachable once the first two have succeeded, and those are patched. It matters a great deal if you have not patched.
Why did a fix exist in July but not reach us?
Ivanti says it found part of this vulnerability through its own product security program and fixed it in the July 25.1.3.0 release, then worked on backporting to the other supported branches when exploitation started. The uncomfortable detail sits in the same advisory: moving to 25.1.3.0 requires new hardware, the ISA4500, ISA6500 or ISA8500, or rebuilt virtual appliances. A fix that requires a hardware refresh is not a fix most customers can take inside a maintenance window.
Should we rebuild the appliance or just patch it?
Patch immediately either way, because it is in KEV with a federal deadline of October 16, 2026. Whether you also rebuild depends on whether the device was exposed before you patched and whether you can actually rule out compromise, which for this chain means forensics rather than a tool result. CISA's standing guidance for compromised appliances of this class is a factory reset, restore from known-good backup, and rotation of all credentials and certificates on them. The appliance's own Active Directory service account belongs on that rotation list and is routinely forgotten.
CONFIDENCE AND LIMITATIONS

Volexity's report is the only detailed account of this activity and it is a single vendor's incident response work, so the tradecraft below rests on one source. Volexity is explicit about its own uncertainty and I have carried that across rather than flattening it: it assesses with low confidence that UTA0576 is criminally rather than espionage motivated, with high confidence that the activity was preparation for lateral movement, and with medium confidence that the actor used large language models in exploit development. It also states that the extent to which the actor's cleanup steps succeeded has not been fully established. One discrepancy I could not resolve: Volexity dates exploitation from October 3, while reporting elsewhere cites a Defused observation from October 1, and a Volexity researcher is quoted saying late September activity would not surprise him. I have used October 3 as the confirmed date and named the rest as unconfirmed. The third flaw in the chain had no CVE and no patch when I checked on October 15, 2026, and that is the most perishable fact here. CVSS vector strings differ trivially between Ivanti, which publishes a 3.0 vector, and NVD, which publishes 3.1; the score is 8.6 in both.
