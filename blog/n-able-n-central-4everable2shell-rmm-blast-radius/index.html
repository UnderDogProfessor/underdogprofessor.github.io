Supply chain/Incident breakdown/November 13, 2026

The miner was the cheap part

Attackers put a Monero miner on 21 N-central servers, 19 already on the newest build. On an RMM, a miner is not the incident. It is the receipt.

SHREYAS LIPARE · GCIH · CEH MASTER

MSPs and IT teams running on-premises N-able N-central, and anyone whose recovery plan assumes the RMM is available.

Researched and drafted with AI assistance, then reviewed and edited by Shreyas Lipare before publication. Every source below was checked against the original.

A vendor telling customers to shut down its product is not a sentence you read often. N-able took its hosted N-central environments offline last week and urged on-premises customers to power their servers down [2].

Then the update meant to end it shipped, and two days later two more exploit chains were published against that update. Within hours, researchers reported cryptominers running on twenty one N-central servers. Nineteen of them were on the new build [2].

The payload is the part worth sitting with. Somebody reached root on a platform that administers other organizations’ endpoints, and used it to mine Monero.

What happened

N-central is a remote monitoring and management platform. MSPs and internal IT teams use it to monitor, manage and secure customer devices, which means the server holds standing administrative reach into every environment it manages [2].

On November 12, 2026, an independent researcher published two exploit chains, 4EverAble2Shell and Agent2Shell, both tested against N-central Appliance 2026.4.1.26 HF2, the emergency build N-able had released on November 10 [2]. The first reaches root on the server without authenticating. The second targets agent functionality and is claimed to reach SYSTEM on managed Windows devices [2].

The server chain combines CVE-2026-90436, a flaw in Apache Axis 1.x, with a separate N-central privilege escalation [2]. Axis carries a CVSS of 9.8 and is marked “UNSUPPORTED WHEN ASSIGNED” in its NVD record, which also states that the Apache Axis project “does not expect to create an Axis 1.x release fixing this problem” [1]. The N-central half had no CVE of its own at the time of writing.

N-able’s position on scope, quoted in its advisory, is that “the server issue described depends on a non-default configuration in which the Legacy API is turned on and exposed to the public internet. Legacy API is turned off by default in the product and is not recommended” [3]. The company has since restricted features and integrations, turning off the Intune integration while remediation continues, and is telling on-premises customers to upgrade Agents and Probes and confirm Legacy API is disabled [4].

The researcher has been publicly critical of the vendor’s patching pace, and told BleepingComputer that releasing the research directly was simply easier than waiting [2]. Two unrelated remote code execution issues reported to the company in July were, by that account, still unpatched [2].

Why this matters

An RMM is not one more server. It is the thing that has agents everywhere, runs commands as SYSTEM by design, and is trusted by every endpoint it touches because that is its entire function. Root on it is not a foothold in one network. For an MSP it is a foothold in all of them at once, and the customers concerned have no visibility into the decision at all.

That inverts the usual third-party conversation. The risk here does not arrive through a vendor’s software update, which is the supply-chain story everybody has rehearsed. It arrives because the management plane itself is reachable and the people managed through it are downstream of a configuration they never saw.

For the organizations in that position, the practical question this week was not “when is the patch”. It was “can we operate with the RMM switched off”, because that is what the vendor asked people to do before any fix existed. Most teams have never tested that. Patching, monitoring, alerting and remote support frequently all route through the same console, so turning it off removes the tooling and the visibility in the same motion.

And there is a smaller lesson with a wider reach. Two of the three technical preconditions here are age rather than negligence: a SOAP interface kept for compatibility, and an end-of-life Java library that will not be fixed because the project that owns it has stopped shipping releases. Both are the kind of thing that survives procurement because nothing in a renewal asks about them.

Technical breakdown

The Axis stage is worth understanding precisely, because it explains why authentication did not help.

NVD describes a deserialization issue in how Axis 1.x handles an inbound SOAP fault. When a fault carries an exception name element, Axis loads the named class, and loading alone runs that class’s static initializer. With a suitable class already on the application’s classpath, that becomes code execution. The record then states the part that matters operationally: “The fault is parsed while the engine resolves the target service, before any per-service handler chain runs, so authentication handlers configured on a service do not protect against it” [1].

So the request never reaches the stage where credentials would be examined. The work happens during routing.

That gets an unauthenticated attacker code execution in the context of the service. The published chain then combines it with a local privilege escalation in N-central to arrive at root [2]. The second chain, Agent2Shell, takes a different route entirely, through the agent channel, and is claimed to reach SYSTEM on managed Windows hosts [2]. Those are separate problems with separate preconditions, which is why disabling the Legacy API addresses one and not the other.

For detection, the useful anchor is the Legacy API endpoint itself. Reporting on the chain points at requests to /dms/services/ServerUI, particularly those referencing a Java class used to reach execution, jline.internal.TerminalLineSettings. On the host, the reported artifacts of the observed campaign are a systemd unit and miner files in temporary directories:

systemd unit:   xvd.service
files:          /tmp/.xvd        /var/tmp/.xvd
process:        XMRig cryptominer

Those indicators belong to one campaign. They are evidence of this actor, not a test for compromise generally, and their absence proves nothing.

Which brings back the payload. An actor holding root on an RMM can reach the estates it manages, push to agents, read stored credentials and operate with the legitimacy of the tool. What this one did was mine cryptocurrency. The most plausible readings are that a commodity operator got there on a public exploit without understanding the ground they had taken, or that mining is simply what happens first while access is resold. Both readings carry the same instruction for anybody who finds it, and the instruction is not “remove the miner”.

What defenders should do next

Immediate, within 24 hours.

  1. Establish whether Legacy API is enabled on each on-premises N-central server. Where it is, disable it. Where it genuinely cannot be disabled, remove it from the internet [3][4].
  2. Upgrade Agents and Probes. N-able states that HF1 changed how the two communicate and that upgrading both is required for managed devices to keep communicating and patching [4].
  3. Search for the reported indicators above, and treat a hit as root-level compromise of the server rather than as a malware finding.
  4. Confirm whether your N-central server has ever been internet-exposed, and for how long. That window, not the patch date, is your hunting scope.

Near term, this week.

  1. Decide in advance what you do when a management platform must be switched off, and write it down. Which tasks stop, which have a manual path, how you patch and how you see endpoints meanwhile.
  2. Review what the N-central service account and stored credentials can reach in each managed environment, and rotate what a root-level compromise would have exposed.
  3. If you are a customer of an MSP, ask which RMM manages your estate, whether it is on-premises, and what that provider did this week. You are entitled to the answer and the question takes a minute.

Structural, this quarter.

  1. Inventory the non-default settings on every management platform, not just patch levels. This incident turned on one of them, and an inventory of versions would not have found it.
  2. Add end-of-life components to third-party reviews. A library that will never receive another release is a permanent finding, not a scheduled one, and asking about it is cheap at renewal.
  3. Segment and monitor the management plane as its own tier. An RMM reaching every endpoint should not sit in the same trust zone as the endpoints it reaches.

Checklist

  • Legacy API confirmed disabled, or confirmed off the internet
  • Agents and Probes upgraded per the HF1 communication change
  • Reported indicators hunted across N-central hosts
  • Any hit treated as full server compromise and rebuilt, not cleaned
  • Internet exposure window established and used as hunting scope
  • Stored credentials and service account reach reviewed and rotated
  • Written plan for operating with the RMM unavailable
  • End-of-life components added to third-party review questions

The access was worth more than the payload

The thing to take from this week is not a lesson about one product. It is that the management plane has quietly become the highest-value target in most estates, and it is routinely treated as infrastructure rather than as a crown jewel. It gets a maintenance window, not an architecture review.

My position is that an RMM deserves the controls an organization gives its domain controllers, and almost nowhere does it get them. It is internet-facing far more often, it carries standing credentials into other people’s networks, and when something goes wrong the only lever anybody has is to turn it off and lose their tooling at the moment they most need it. That is not a patching problem. It is an architecture that nobody chose deliberately and everybody inherited.

The miner is the detail I keep returning to, because it is the clearest statement of the gap. Somebody held administrative reach into an unknown number of managed networks, and converted it into a few dollars a day of Monero. The next operator who reaches that position may be better informed about what it is worth, and the preconditions that got the first one there have not changed.

FREQUENTLY ASKED

Am I affected if Legacy API is off?
N-able's initial review says the server issue depends on a non-default configuration where Legacy API is turned on and exposed to the internet, and that Legacy API is off by default and not recommended. That is the vendor's framing of the server chain. It does not cover Agent2Shell, which targets agent functionality rather than the Legacy API.
Does installing Hotfix 2 fix this?
No. Both new exploit chains were published as tested against the 2026.4.1.26 HF2 build, and of the 21 servers reported compromised, 19 were already running it. HF2 addressed the earlier Able2Shell disclosures, not these.
Is there a CVE for the whole chain?
Not for the chain. The first stage is CVE-2026-90436 in Apache Axis 1.x, scored 9.8. The N-central privilege escalation that turns that into root had no CVE at the time of writing, so tracking this by CVE alone will miss it.
We found a cryptominer on our N-central server. Is that the whole problem?
No. Treat it as evidence of root-level compromise of a platform that administers your clients' endpoints. The miner is what this particular actor chose to run with that access, not the limit of what the access allows. Rebuild rather than clean.
What can we actually do while there is no fix?
Confirm Legacy API is disabled, and where it genuinely must stay on, take it off the internet. Upgrade Agents and Probes, which N-able says is required after HF1 changed how they communicate. Then hunt, because those steps do not tell you whether you were already reached.
CONFIDENCE AND LIMITATIONS

The count of 21 affected servers comes from researcher reporting relayed by journalism, not from a vendor or government statement, and could not be independently verified here. N-able's initial review frames the server issue as depending on a non-default configuration; independent researchers report compromise of production servers. Earlier coverage described probing with exploitation unconfirmed, later coverage describes active exploitation, so the picture moved during the week. N-able's advisory could not be opened directly from here and is quoted below as Decipher and The Hacker News quote it. Huntress's write-up returned 403 to every route tried.
